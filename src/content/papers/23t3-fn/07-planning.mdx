## The Question

The domain description of a Blocks World with a single one-armed robot is given below.

**PREDICATES**
```text
armEmpty     The arm is not holding any block, it is empty.
holding(X)   The arm is holding X.
onTable(X)   X is on the table.
clear(X)     X has nothing above it, it is clear.
on(X,Y)      X is directly placed on Y.
```

**OPERATORS**

`Pickup(X)`: pick up X from the table.
```text
Preconditions: { armEmpty, clear(X), onTable(X) }
Add Effects  : { holding(X) }
Del Effects  : { armEmpty, onTable(X) }
```

`Putdown(X)`: place X on the table.
```text
Preconditions: { holding(X) }
Add Effects  : { armEmpty, onTable(X) }
Del Effects  : { holding(X) }
```

`Unstack(X,Y)`: pick up X sitting on Y.
```text
Preconditions: { armEmpty, clear(X), on(X,Y) }
Add Effects  : { clear(Y), holding(X) }
Del Effects  : { armEmpty, on(X,Y) }
```

`Stack(X,Y)`: place X onto Y.
```text
Preconditions: { holding(X), clear(Y) }
Add Effects  : { armEmpty, on(X,Y) }
Del Effects  : { holding(X), clear(Y) }
```

## The Topic in 60 Seconds

| Test | Against | Pass condition |
|---|---|---|
| Applicable | start state | $\text{PRE}(a) \subseteq$ state |
| Relevant | goal | ADD writes ≥1 goal literal AND DEL destroys none |

## 6.1 — Applicable → `A,B`

Mechanical filter. The decisive questions:

1. **Is the arm empty?** If yes → only Pickup/Unstack candidates live (Stack/Putdown need `holding`). If a block is held → only Stack/Putdown live.
2. For each remaining candidate tick preconditions against the state: buried blocks fail `clear`, stacked blocks fail `onTable`.

Exactly two survivors in this instance → keyed `A,B`.

## 6.2 — Relevant → `C,D,E`

Writer-hunt over the goal:

| Goal literal shape | Sole writer family |
|---|---|
| $\text{on}(X,Y)$ | `Stack(X,Y)` — exactly one writer |
| $\text{onTable}(X)$ | `Putdown(X)` |
| $\text{clear}(Y)$ | Unstack / Pickup family |

Then veto writers whose DEL list touches any goal literal. Three goal literals ⇒ typically three writers survive → keyed `C,D,E`.

Argument-order alarm: `Stack(C,B)` writes `on(C,B)` ≠ `on(B,C)`; reversed pairs are always planted distractors.

## 6.3 — Layer-1 action mutexes → `A,B,C`

Layer 1 = the applicable set from 6.1. With ONE arm:

- Any two actions toggling the arm (`armEmpty` ↔ `holding`) have **inconsistent effects**: one deletes what the other adds/needs ⇒ mutex.
- Competing needs add pairs whose preconditions contradict at L0 (e.g., `clear(Y)` vs `on(Z,Y)`).

For a two-action layer there is exactly ONE unordered pair — keyed `A,B,C` enumerates it plus its optioned orderings/duplicates. Any option naming an action absent from layer 1 is auto-wrong.

## 6.4 — Layer-2 proposition mutexes → `A,B`

Build the producer mini-table for L2 propositions (adds of layer-1 actions):

| Pair type | Producer pairing | Verdict |
|---|---|---|
| `holding(X)` vs `armEmpty`-class facts | grabber vs the other arm action | mutex if producers fight |
| two facts from the SAME action | same producer | never mutex |
| facts whose only producers are the mutexed pair | all cross-pairs mutex | mutex |

Keyed `A,B` names the optioned pair(s) passing the double test — quote "every way of getting p fights every way of getting q".

## Tricks & Tips

<Accordion title="Exam shortcuts">
1. Solve 6.1 first - layer 1 IS the applicable set, so 6.3 inherits it wholesale.
2. Arm-clique rule: any pair of actions both toggling the arm conflict - generates nearly every layer-1 mutex instantly.
3. Relevance = writer hunt + deleter veto; usefulness plays no role and neither does current applicability of the writer.
4. Producer tables settle 6.4 mechanically: same-action facts are safe, all-cross-mutex facts die together.
5. Underline argument order everywhere: on(C,B) vs on(B,C) flips verdicts in both relevant-literal and mutex checks.
</Accordion>

**Answers:** 6.1 `A,B` · 6.2 `C,D,E` · 6.3 `A,B,C` · 6.4 `A,B`
