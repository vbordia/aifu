## The Simplest Explanation

Minimax wastes effort on branches that could **never influence the final decision**. Alpha-beta's insight:

> *"While backing up values, keep track of the best already-guaranteed options for both sides. If a branch turns out worse than something already guaranteed — stop looking. Cut it off."*

Two values travel down the tree:

- **α (alpha)**: the best value MAX is already assured of *somewhere else* (lower bound). Starts at $-\infty$.
- **β (beta)**: the best value MIN is already assured of (upper bound). Starts at $+\infty$.

**The cutoff rule**: whenever $\alpha \geq \beta$, stop expanding the current node and return. Nothing below can change the outcome.

<Callout type="tip" title="Remember This">
Alpha-beta returns the EXACT same root value as minimax — it just skips work that cannot matter. α is "how good MAX's fallback is", β is "how good MIN's fallback is". When they cross (α ≥ β), the current branch is dead.
</Callout>

## The Rules (memorize these four lines)

1. At a **MAX node**: update $\alpha \leftarrow \max(\alpha, \text{child value})$
2. At a **MIN node**: update $\beta \leftarrow \min(\beta, \text{child value})$
3. Children inherit the current $(\alpha, \beta)$ window
4. If at any point $\alpha \geq \beta$: **prune** remaining children of this node and back up immediately
   - If cut off at a MAX node → called a **β-cutoff**
   - If cut off at a MIN node → called an **α-cutoff**

### How to Count Cuts in Exams

A cut fires the moment a node's provisional value becomes **≤ α** (at MIN nodes) or **≥ β** (at MAX nodes), using the inherited window. Count every sibling after the firing child as pruned — even if the firing child was last, some papers still ask "was there a cutoff?" (answer: the condition held).

## Inverse Design Problems (2026 trend!)

Recent exams flip the question: *"Assign evaluation values to maximize the number of cuts."*

Strategy:
- To force an early **α-cutoff** at a MIN node under window $(\alpha, \beta)$: make its **first** leaf ≤ α (e.g., very negative)
- To force an early **β-cutoff** at a MAX node: make its **first** leaf ≥ β (e.g., very large)
- Left-to-right order matters: cuts only fire on children examined **after** the window tightened, so put extreme values early in promising subtrees and let later siblings be cut

## Effectiveness

| Scenario | Leaves evaluated |
|----------|-----------------|
| Worst ordering (best moves last) | $b^{m}$ — no savings, equals plain minimax |
| Random ordering | $\approx b^{3m/4}$ |
| **Best ordering (best moves first)** | $\approx b^{\lceil m/2 \rceil} + b^{\lfloor m/2 \rfloor} - 1$ ≈ doubles searchable depth! |

With perfect move ordering alpha-beta searches roughly **twice as deep** as minimax in the same time — why it powers every chess engine.

## Inspected vs Pruned — Two Sides of One Trace

Papers flip between asking which leaves were **pruned** (skipped) and which were **inspected** (evaluated). They're complements:

$$\text{inspected} \cup \text{pruned} = \text{all horizon leaves}, \qquad \text{inspected} \cap \text{pruned} = \emptyset$$

| Question phrasing | What to output |
|-------------------|----------------|
| "List the horizon nodes pruned by Alpha-Beta" | skipped leaves, sorted |
| "First five horizon nodes pruned" | skipped leaves in **chronological cut order**, not alphabetical! |
| "Leaf nodes inspected by Alpha-Beta" (25T2) | evaluated leaves — everything not pruned |
| "Leaves not affecting the game value" (24T3) | leaves whose value cannot change the root under optimal play — typically deep pruned branches |

The chronological variant matters when several cuts fire: order them by *when* the cutoff occurred during the left-to-right traversal, then sort alphabetically only within simultaneous cuts.

### Cutoff Taxonomy

When a forced eval triggers a stop, name it correctly:

| Where the window closes | Node type | Cut name |
|------------------------|-----------|----------|
| value ≤ α reached | MIN node | **α-cutoff** |
| value ≥ β reached | MAX node | **β-cutoff** |

25T3 papers ask this directly: give a leaf eval that induces a cutoff at a named node, then classify it. Recipe: check whether the node is MIN or MAX; that fixes α-cut vs β-cut; solve the inequality for the leaf's smallest/largest feasible value.

<Accordion title="Common Exam Pitfalls">
1. **Not propagating the window correctly**: children inherit the CURRENT (α, β) of their parent's context — updated as ancestors' values tighten. Writing stale windows is the most common trace error.

2. **Cutting too eagerly or too little**: the rule is exactly α ≥ β (some books write β ≤ α at MIN nodes). Equal counts! A value equal to the bound still triggers a cutoff.

3. **Forgetting which side updates which bound**: MAX raises α; MIN lowers β. Swapping these scrambles every subsequent cutoff decision.

4. **Miscounting pruned leaves in 'count the cuts' questions**: siblings AFTER the triggering child are pruned; the triggering child itself was examined. Draw an arrow where the cut fires.

5. **Assuming SSS\* beats alpha-beta in node count**: SSS\* never evaluates MORE nodes than alpha-beta (it can evaluate fewer), but costs far more memory. See the SSS\* page for the comparison table.
</Accordion>
